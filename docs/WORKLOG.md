Any failure is pushed to `OPS_ALERT_WEBHOOK_URL` through `node dist/api/cli.js alert --text "backup check FAIL: …"` (`compose run --rm --no-deps api`), so a broken backup pages instead of waiting for a restore to fail. ## 2026-11-04 — Tier C was written and rehearsed, and the rehearsal killed the word "demote"

- The audit finding is that api/worker connect as `line_ccc`, which is `superuser` + `BYPASSRLS`. The plan was to take those attributes away. **PostgreSQL will not let you do that to the role initdb was told to create**: `alter role line_ccc with nosuperuser` → `ERROR: permission denied to alter role / DETAIL: The bootstrap user must have the SUPERUSER attribute.` The staging compose file sets `POSTGRES_USER: ${POSTGRES_USER:-line_ccc}`, so `line_ccc` *is* that role. This is not a misconfiguration to fix — it is why Tier C had to be redesigned before a single line of it reached staging.
- **`NOBYPASSRLS` on a superuser is decoration, and `015_tier_c_app_role.sql` deliberately does not set it.** Rehearsed: after `alter role line_ccc with nobypassrls`, `pg_roles.rolbypassrls` read `f` while the role still counted all 7 campaigns and inserted new rows — superuser-ness bypasses RLS independently of the flag. Setting it would make the next audit pass while changing nothing, which is worse than leaving the finding open.
- So the proposal separates *connections* instead of subtracting privileges: `line_ccc` stays owner + superuser and is used only for migrate/DDL/backup/restore, while a new `line_ccc_app` (`NOBYPASSRLS`, not the owner, `connection limit 20` over `DB_POOL_MAX=5` × two processes) becomes the runtime role, with one permissive `<table>_app_access` policy per RLS-enabled table.
- **The policy block is the load-bearing part, and its absence fails silently.** Tier B left every table with `relrowsecurity = true` and zero policies, which for a non-owner is deny-by-default. Rehearsed with a throwaway role carrying the same DML grants but no policy: `select count(*) from campaigns` → **0 rows, no error**; `update`/`delete` → `UPDATE 0`/`DELETE 0`; `insert` → `ERROR: new row violates row-level security policy`. A backend in that state does not crash — it serves an empty admin panel to an operator who then wonders where the customers went. That failure mode is why the file carries no `BEGIN`/`COMMIT` and must run as `--single-transaction -v ON_ERROR_STOP=1`.
- Rehearsal environment had to reproduce staging, not a fresh DB: `postgres:16-alpine` with `POSTGRES_USER=line_ccc`, migrations 001–014 + seed via `node dist/api/cli.js setup`, **then `013_rls_grant_tier_ab.sql`** to get to RLS 27/27 with 0 policies.
